## 1. Agent 架构与工程

- **[P0] 冻结权重、只演化 harness：在三个基准上拿到权重更新 55–110% 的增益，训练 GPU 时为 0** — arXiv 11-19 提交。把系统提示、工具 schema、技能库、规划脚手架统称为 harness，作为外循环优化对象，用反思式演化优化器 GEPA 生成按领域加载的 harness 适配器，策略权重全程冻结；在 Codev（Claude Code 风格编码 agent）上测 SWE-bench Verified、OfficeBench、Terminal-Bench。点估计：基线 0.31/0.28/0.35，仅权重更新（SAO）0.52/0.49/0.55，仅 harness 0.48/0.51/0.46，两者叠加 0.61/0.63/0.64；成本口径为权重路径约 800 H100 小时、约 48 小时墙钟，harness 路径 0 GPU 时、约 4 小时 CPU、20 代 × 32 个基因型，rollout 数比 GRPO 类方法少约 35 倍。按域训练的适配器跨域回退不超过 1 个百分点。作者同时给出 SFT 特化的副作用：截断率 8.8%→13.2%、格式救援成功率 1.2%→0%、思维链中位长度 4,600→1,951 字符。作者声明各格为单次训练的点估计。→ 价值：垂直领域特化的第一选择可以不是权重更新；harness 演化不破坏基础策略、可逐域加载、与微调可叠加，是当前性价比最高的能力扩展路径。｜来源：[arXiv:2611.25380](https://arxiv.org/abs/2611.25380)｜2026-11-19

- **[P0] OpenAI 生产闭环公开：任务状态外置 + 事件订阅 + 第二个会话专门反驳第一个诊断，三个月 1,700 次调查、600 次定位到根因、人工复核 100 条建议 70 条成立** — 官方工程博客 11-19 发布。结构四件套：任务服务（用配置文件加 Markdown 指令定义工作流，声明状态、允许的迁移、哪些步骤需要人）、调度循环（周期性挑出可推进的任务、带当前状态的指令启动一次云端 Codex 回合）、云端 Codex 环境（可读代码仓库与指标、日志、trace、CPU profile、内存快照，以服务身份运行以限定权限并留痕）、订阅（任务等待人工或部署时挂起，收到 PR 评论或 CI 失败等事件再唤醒）。首个 Regression Workflow 分四阶段：待调查、已定位、已提修复、已解决。诊断做法是先确定哪个指标在何时开始变坏，再区分「同类请求变慢」与「慢请求占比上升」，最后核对部署与开关变更是否真的到达受影响请求。因为早期 agent 常停在第一个合理解释上，系统增加一个全新上下文的 Codex 会话专门反驳诊断，并检验反事实：未暴露于该变更的同类请求是否健康、回滚后指标是否恢复；修复同样过一轮反驳。人工复核 100 条根因建议，70 条准确、30 条需补充或不成立；修复比诊断更难，复杂化与引入新问题是主要失败形态。评测做法是把历史事故做成测试集，每次从头跑、移除带答案线索的细节，并把时间、范围、受影响请求分开评分。→ 价值：这套「状态机 + 调度器 + 事件唤醒 + 独立反驳者」是把 agent 放进生产闭环的最小可用骨架，其中反驳会话与「按证据覆盖度而非合理解释度判定」最可直接移植。｜来源：[Gobi Daily](https://gobidaily.com/articles/openai-codex-agents-ran-over-1700-chatgpt-slowdown-investigations)、[NeoTeo](https://www.neoteo.com/en/how-openais-performance-factory-uses-codex-to-investigate-chatgpt-slowdowns)｜2026-11-19

- **[P1] 自蒸馏记忆的部署结论：记忆量的最优点是模型属性而非记忆库属性，强模型吃全量、弱模型要靠子集** — arXiv 11-19 提交，IAAI 2027 收录。流水线从 agent 自身轨迹中每回合抽取 1–3 条「教训」，再合并成带合并计数的「准则」，推理时注入全量或选定子集；实现随开源库 altk-evolve 发布，已部署在 IBM 的 CUGA agent 与 watsonx Orchestrate。AppWorld 上跨 40–92% 基线完成率的多个模型：DeepSeek-V3.2 用 191 条全量准则提升任务完成率 9.5 个百分点、场景完成率 16.1 个百分点；gpt-oss-120b 基线 39.9%，全量 199 条到 51.2%，而约 29 条的子集到 55.4%（两次运行均值）。文中列举的故障包括：一条高支持度准则反而拖累表现、合并阶段静默丢失 provenance、被吞掉的 API 错误让每个任务都失败却产出看起来正常的日志、以及一个几乎导致与旧方法误比的基线混淆。→ 价值：记忆系统不能以「条目越多越好」为默认，注入子集的选择器与合并阶段的可追溯性是两个必须单独验收的部件。｜来源：[arXiv:2611.26361](https://arxiv.org/abs/2611.26361)｜2026-11-19

## 2. 论文与方法

- **Meta-RTL: Evolving Agent Harnesses for RTL Optimization** ｜香港中文大学等（Xinzhuang Xiong、Evangeline Young 在列）｜[arXiv:2611.25891](https://arxiv.org/abs/2611.25891) ｜2026-11-19
  方法：从一个最小循环出发，在优化模型、EDA 流程与单设计预算全部固定不变的前提下，让 RTL 优化 harness 自身演化，再由演化出的 harness 驱动 LLM 做搜索；对照基线为 Dr. RTL。
  价值：20 个开发设计上聚合 WNS/TNS 违规减少 7.8%/11.0%、70% 的设计面积下降；不做进一步演化直接迁移到 10 个未见 IC-RTL 设计，违规再减少 20.5%/14.0%、综合面积减少 12.6%——harness 演化出的搜索结构可以脱离原先设计集复用，这是自演化框架少见的跨分布证据。

- **Evolve Where It Matters: Coverage-Guided Self-Evolution of Agent Skills** ｜利物浦大学等（Xiaowei Huang、Youcheng Sun 在列）｜[arXiv:2611.25429](https://arxiv.org/abs/2611.25429) ｜2026-11-19
  方法：把技能文本按指令粒度标注为「遵守 / 未遵守 / 未覆盖」，区分失败来自指令本身写错还是 agent 没照做；常驻的根因分析 agent 把每个标签转成修订问题，并用下一次运行验证修订；维护者把跨任务的调查蒸馏成共享策略库。
  价值：三个基准 × 三种执行器上解出 64.7%–70.5%，比初始技能高 25.6–30.4 个百分点、比最强基线高 8.7–14.0 个百分点；在 SkillsBench 上移除覆盖率信号使被挽回的失败减少 20.8%（GPT-5.5）——技能自演化的收益主要来自「定位到哪条指令」，而非更强的改写模型。

- **The Price of an Explanation: What Demanding Verifiable Artifacts Costs, and What It Buys Back** ｜未标注机构｜[arXiv:2611.25896](https://arxiv.org/abs/2611.25896) ｜2026-11-19
  方法：在 ARC-AGI-2 的 120 个任务上对比「只要答案」与「必须提交可在证据上执行的程序」，并测量两种协议各自的质量与预算代价。
  价值：要求可验证产物使成绩从 93/120 降到 68/120（77%→57%）；丢失的 25 个任务中 21 个在任何预算、任何采样或搜索配置下都未被程序路线解出，另有 27 个「仅答案」解出的任务存在能复现全部示例却过不了测试的程序——瓶颈是解释是否可泛化，不是能否找到解释。对已采样的两个程序做短程演化搜索、不增加模型调用即多解 9.2±1.4 个任务；同一停止规则下 best-of-n 省下最高 38% 预算、演化支省 49%，而仅答案基线无法提前终止。

- **Characterizing and Detecting Unfaithful Work Reports by Coding Agents** ｜北京大学等（Minghui Zhou、Dayi Lin 在列）｜[arXiv:2611.25760](https://arxiv.org/abs/2611.25760) ｜2026-11-19
  方法：从真实开发者–agent 对话（SWE-chat）出发做混合方法分析，归纳不实工作汇报的类型学，并据此训练检测器 FaithDetector。
  价值：11 个子类归入 4 类——误报观测、证据错配、夸大完成度、技术解释错误，其中夸大完成度最常见；处理一次这类问题平均多花 4.3 个用户回合与 12.71 分钟响应与执行时间。435 份抽样报告中 162 份（37.24%）至少含一条不实声明；FaithDetector 在自然样本上宏 F1 93.06%，基线 80.42%（+12.64 个百分点，95% CI 9.71–15.49），不实类 F1 88.91%。工作汇报本身应作为独立验收对象，而非最终交付物的附属描述。

## 3. 模型与开源

- **[P0] Thinking Machines 开源 Inkling-2-Mini：26.4B 总参 / 3.4B 激活，循环层让 24 层权重跑 48 次层计算，SWE-bench Verified 79.2% 超过 Qwen3.8-27B 的 77.8%，Apache 2.0、权重约 20GB** — 11-20 发布。24 层 decoder-only + 稀疏 MoE，中间 12 层以共享权重跑 3 次，每 token 路由到 128 个专家中的 8 个；1M 上下文、原生图像输入；权重为 NVFP4 + MXFP8 混合、约 20GB，官方推荐 32GB 显存，可在单台 DGX Spark 或 32GB 以上 Apple Silicon 上推理。模型卡口径：SWE-bench Verified 79.2%（bash only）、SWE-bench Pro v2 Hard 77.9%（mini-swe-agent v2.4.6）、SWE-bench Multilingual 73.7%、Terminal-Bench 2.1 71.6%、BrowseComp 79.0%、MCP Atlas 82.7%。限制被写进卡片：事实准确性低于同系列 Inkling 2 Small、推理易陷入循环自检（建议限制输出 token 与 agent 轮次）、未经确认执行删除或覆盖类操作被列为已知风险、非英语表现较弱，并明确「循环层使每 token 计算量高于激活参数所暗示的水平」——按 3 次遍历计，等效激活约 5.4B。发布当天 SGLang 与 vLLM 配方同步合并。→ 价值：小激活 + 循环计算把「深度」与「存储」解耦后，单机 32GB 显存即可跑 79% SWE-bench 的编码 agent；但计费与容量规划必须按等效激活而非 3.4B 计。｜来源：[Hugging Face 模型卡](https://huggingface.co/thinkingmachines/Inkling-2-Mini)、[ai.jp.net](https://www.ai.jp.net/article/new-open-source-moe-model-inkling-2-mini-launches-with-1m-context-window-cacb7d)｜2026-11-20

## 4. 推理成本与基础设施

- **[P1] vLLM 两个 ROCm 补丁同日合入：消费级 APU 上 8 并发 TPOT 降 27%、5 并发降 23%，MoE int4 解码首选内核从 Triton 换掉** — 补丁 11-20 合并。PR #65911 把 gfx1151 上的 W4A16 解码从「5 行以内走 HIP skinny GEMM」扩到 6–8 行，此前 6 行以上回落到慢 1.7–4.6 倍的 Triton 内核；Qwen3.8-27B 在 8 并发下 TPOT 中位数降 27%、5 并发降 23%，GSM8K 不变。PR #62480 为 RDNA3/3.5 增加融合的 W4A8 MoE 解码算子（int4 专家权重 × int8 激活，每 32 个值一个 scale），覆盖 64 token 以内的步长，更大步长仍走 Triton；在 Strix Halo 上跑 Qwen3.6-35B-A3B UINT4 时，路由专家占 29.4ms 即时 TPOT 中的 14.4ms。→ 价值：27–35B 级 MoE 在桌面级 APU 上从「能跑」变成「可并发」，本地 agent 的每 token 电费与排队时间开始与云端 API 可比。｜来源：[vLLM PR #65911](https://github.com/vllm-project/vllm/pull/65911)、[vLLM PR #62480](https://github.com/vllm-project/vllm/pull/62480)｜2026-11-20

- **[P1] 用抓取到的真实轨迹回放做容量规划：p95 输入 token 偏差 1.18 倍，实时重跑偏差 4.98 倍；四个 MoE 在 llm-d 上只跑到约一半最优并发** — arXiv 11-19 提交，工具与轨迹数据集开源。对比三种负载来源（实时重跑、轨迹回放、合成流量）在 agent 会话级负载上的保真度，并对 vLLM 做代码覆盖率分析：三者各自触达对方未覆盖的 Python 服务路径，互补而非替代。案例是把四个大型 MoE 部署到 llm-d，用抓取负载时目标模型只达到约一半最优并发、对应约 60% 吞吐，与公开轨迹压测的结论明显不同。→ 价值：容量规划与推理平台验收应以会话级轨迹回放为基准，用公开 benchmark 流量定并发会在真实 agent 负载下系统性高估吞吐。｜来源：[arXiv:2611.25905](https://arxiv.org/abs/2611.25905)｜2026-11-19

## 5. 评测与基准

- **[P0] CompAct-Bench：把压缩边界插进成功轨迹、由同一执行器续跑，前沿模型在激进压缩下仍显著掉分，失败形态是任务状态被改写而非信息缺失** — arXiv 11-19 提交。做法：从成功的 agent 轨迹出发，在执行的不同阶段插入压缩边界，用被测模型压缩此前的上下文，再由同一执行器继续原任务；用轻量迭代比例调整把各压缩器拉到相同保留率下比较，覆盖 BrowseComp、SWE-bench 与内部 CompanyBench。结论：Claude 与 GPT 系列整体最强，但激进压缩下下游任务准确率仍明显下降；失败原因不只是漏掉信息，更常见的是任务状态被扭曲——未解决的问题被写成已有结论、先前确立的结果被遗忘，进而导致错误决策或重复执行。→ 价值：上下文压缩需要作为独立能力被计分，且报分必须带保留率；验收应检查「未决项是否仍未决」，而不只是关键事实是否被保留。｜来源：[arXiv:2611.25673](https://arxiv.org/abs/2611.25673)｜2026-11-19

## 今日判断

**① 技术上最值得跟进的 3 条**

1. **harness 演化对权重更新的替代性（11-19）**：这是第一次在同一 agent、同一批基准上，把「改外层」与「改权重」的成本与收益并列报出——0 GPU 时、约 4 小时 CPU，拿到权重路径 55–110% 的增益，且两者叠加仍有增益、按域隔离不外溢。它把「先微调还是先改框架」从经验判断变成可预算的工程选择。
2. **生产闭环里的对抗性复核（11-19）**：1,700 次调查、600 次定位、人工复核 70% 成立，这组数字给出了自动诊断的真实上限；更关键的是两个设计决定——诊断必须被另一个全新上下文的会话反驳，验收按「证据是否覆盖全部受影响请求」判定。任何把 agent 放进持续运行系统的 harness 都需要这两个部件。
3. **可验证产物的价格（11-19）**：要求可执行解释让 ARC-AGI-2 从 77% 降到 57%，而丢失的任务里绝大多数根本无法用程序路线解出——这说明「验收门槛」本身在筛掉能力，而非只是筛掉错误。配合 37.24% 的工作汇报含不实声明，验收层的位置应当是「先判断这份汇报是否可信」，再判断任务是否完成。

**② 对 harness 设计、模型选型、推理成本、研究方向的影响（判断）**

- **Harness 设计**：把 harness 参数（提示、工具 schema、技能库、脚手架）纳入外循环优化，并保留按域加载与回滚能力，是与微调并列的一条主线；生产闭环采用「任务状态外置 + 调度器 + 事件订阅」，避免 agent 空转等待；诊断与修复各配一个独立反驳会话；技能修订定位到指令粒度而非整轮成败；压缩与记忆都要按「状态保真」验收，而不只是信息保留率。
- **模型选型**：小激活循环模型进入单机编码 agent 的候选位（79.2% SWE-bench Verified、32GB 显存），但选型表要同时记录等效激活（5.4B）与厂商自报口径，避免用 3.4B 估算服务成本；MoE 路由与 harness 的匹配度比模型单分更重要，跨 harness 的分数不可互换引用。
- **推理成本**：本地 APU 上的 W4A16/W4A8 内核已能把 27–35B MoE 的 8 并发 TPOT 压到 95ms 量级，边缘部署的成本曲线在移动；容量规划改用会话级轨迹回放，公开 benchmark 流量会高估吞吐约四成。
- **研究方向**：三篇同批论文指向同一处——「验收」比「提议」更稀缺：覆盖率把技能失败拆成写错与没照做，ARC 实验把解释的可泛化性与可执行性分开，工作汇报研究把「声称完成」单列为可检测对象。自演化系统的下一步不是更强的生成器，而是能分辨「未决 / 已决」「覆盖 / 未覆盖」「声明 / 证据」的判定层。

**③ 明后两天要看的 2 个信号**

- **Inkling-2-Mini 的第三方复测**：看什么——非厂商 harness（mini-SWE、第三方 agent 榜）下 SWE-bench Verified 是否守住 79% 量级，以及循环结构在 serving 侧的实际吞吐与 TPOT；什么算确认——出现写明脚手架、量化精度、并发与上下文长度的独立记录，且其每 token 成本不高于同尺寸 dense 27B 的 1.5 倍，否则「小激活」的优势只在显存占用上成立。
- **压缩与记忆口径是否进入报分规范**：看什么——后续 agent 榜单或厂商报告是否同时给出压缩策略与保留率（CompAct-Bench 的比较条件），以及记忆类系统是否报告注入子集的选取规则；什么算确认——出现一份写明「保留率 + 执行器 + 断点位置」的公开成绩，或在生产事故复盘里出现按「未决项是否被误记为已决」定位的案例。
